# Limitations and Security Considerations

## 1. Threat Model and Adversary Assumptions

1. **Semi-Honest vs. Active Malicious Security**:
   - Our primary benchmark aligns OpenFHE 3-party Threshold BFV-RNS (`threshold_bfv_128` with `NOISE_FLOODING_MULTIPARTY`) and MP-SPDZ 3-party additive secret sharing (`semi_dishonest_majority_3p`) in the **semi-honest (passive) dishonest-majority threat model** ($t \le 2$ of $3$).
   - While `NOISE_FLOODING_MULTIPARTY` protects against passive key-recovery attacks from partial decryptions, full active malicious security in threshold FHE requires attaching Zero-Knowledge Proofs of Plaintext Knowledge (ZKPoPK) and proofs of correct partial decryption ($\Sigma$-protocols), which are not natively generated by OpenFHE's standard `MultipartyDecryptMain` API.
   - Conversely, MP-SPDZ provides built-in active malicious protocols (`malicious-shamir-party.x` and `mascot-party.x`), which we include as secondary comparison profiles in `config/smpc.yaml`.
2. **N-out-of-N Threshold Decryption Availability**:
   - In 3-out-of-3 Threshold BFV (`kp_c = cc.MultipartyKeyGen(kp_b.publicKey)`), all three organizations must participate in `MultipartyDecryptFusion` to decrypt the final result. If one organization goes offline permanently, decryption cannot complete without a fallback secret-key recovery threshold mechanism.

## 2. Network Emulation Scope

1. **Shared Interface Traffic Control (`lo` / `eth0`)**:
   - Inside the single-container orchestrator (`benchmark`), all three MP-SPDZ participant processes (`P0`, `P1`, `P2`) and the OpenFHE TCP transport sockets communicate over the container's shaped Linux loopback interface (`lo`) controlled via `tc qdisc ... netem`.
   - While Linux `netem` accurately enforces per-packet propagation delay, jitter, packet loss, and token-bucket rate limiting (`rate <R>mbit`), a shared container CPU schedules all three participants on the same multi-core processor (12 logical CPUs). Under heavy CPU saturation, local context-switching can slightly increase effective latency compared to three physically separate bare-metal servers.
2. **Docker Privilege Boundaries**:
   - Applying Linux `tc`/`netem` rules requires the `CAP_NET_ADMIN` Linux capability (`cap_add: [NET_ADMIN]` in `docker-compose.yml`). Full `privileged: true` mode is intentionally avoided to preserve container isolation and host network safety.

## 3. Arithmetic Domain Constraints

1. **Exact Integer vs. Fixed-Point Division**:
   - Both BFV-RNS and prime-field SMPC (`-F 64`) natively operate over finite rings/fields ($\mathbb{Z}_p$ and $\mathbb{F}_p$) where exact integer addition and multiplication are closed operations, whereas non-linear division requires either polynomial approximation or bit-decomposition circuits.
   - As documented in `config/experiment.yaml` (`division_policy: post_decryption_exact`), Workload 1 (`aggregation`) computes the exact encrypted/secret-shared integer `SUM` and `COUNT = N`, and performs floating-point division `AVERAGE = SUM / COUNT` upon authorized output reconstruction.
